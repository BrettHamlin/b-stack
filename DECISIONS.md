# Decisions

For the human owner: what we decided and why. Agents work from `skills/`, `rules/` and `starters/`, not this file.

## Purpose

b-stack lets anyone clone it and have an agent set up a new app where quality is **enforced, not requested**. It started from Lauren Tan's talk *All Code Is Slop (Except Mine)* (`research/`) and goes beyond it.

## Core beliefs

- **Agents repeat the same mistakes** across runs, so a check pays off every time it fires. Correcting in chat fixes one instance.
- **Every agent session is a new hire on day one.** Onboarding aids (paved paths, obvious structure) are needed permanently.
- **Code is the agents' memory.** They copy existing patterns, so the first patterns in a repo become the template. Enforcement must exist from the first commit.
- **Architecture first, enforced right away.** A rule needs a correct path to point to; architecture is a decision, a rule makes it executable.
- **Verification is now cheap** (property tests, models, journey checks), so use it.
- **Don't automate a bad loop.** One reliable agent loop comes before triggers and fleets.

## The enforcement pyramid

Sorted by how hard each layer is to get around (Lauren's sorts by kind of thing):

| Layer | Meaning | Enforced by |
|---|---|---|
| 1. Can't be written | The wrong thing won't compile | Types, modules, compiler settings |
| 2. Can't be merged | A check blocks it before `main` | Parsed-code checker in protected CI |
| 3. Can't pass verification | The running product behaves wrong | Journey, property, formal tests |
| 4. Guided | Steers judgment; enforces nothing | Prose (minimal) |
| 5. Judged | Is the intent right? | Human review of evidence |
| Foundation | Nobody weakens the checks unnoticed | CODEOWNERS with a ruleset requiring code-owner review (CI checks it's on), settings checks |

Rule: push every constraint as high as it goes.

| 2026-11-17 | **App and AppVerify compose features the same way:** both call the same view initializer (e.g. `NotificationSettingsView(preferences:)`), which loads the saved value itself; only the services passed in differ. Reproduced with two scratch copies of the starter on one simulator (Xcode 27.2, iOS 27.2, Tuist 4.216.7): on main, B's `check.py` replaced A's installed app and both journeys failed (`kAXErrorServerNotFound`) while A relaunched its app and recorded; with this change B's simulator gates waited 49 s for A's `simulator.py run` session, then all six gates passed, and both checkouts' apps stayed installed. ## Verified findings (Swift 6.4.2, Xcode 27.2, Tuist 4.216.7, SwiftLint 0.65.1, Harmonize 1.3.0)

Most are tested on every run of `scripts/test_rules.py`; `~Copyable`, the `package`/`internal`/actor walls and the import-only purity check were tested by hand. Notable results:

- **Compiler enforces:** distinct ID types, exhaustive switches, `~Copyable` single use, unavailable APIs (with a custom message), warnings as errors, main-actor isolation.
- **Strict settings reject an unneeded `public import`.**
- **Module boundaries are only partly a compiler guarantee.** An undeclared sibling import fails on a clean build only; once the sibling is built, incremental builds accept it. Indirect imports and system frameworks (e.g. `SwiftUI` in Domain) always compile. The checker must cover all three.
- **The compiler accepts every escape hatch** (`@unchecked Sendable`, `nonisolated(unsafe)`, `!`), so other tools must ban them.
- **Tuist `inspect dependencies --only implicit`** catches undeclared sibling and indirect imports (and `--only redundant` catches unused ones), but **not system frameworks**. It only works on Tuist-managed projects.
- **Harmonize** catches disallowed imports including system frameworks, `static let shared`, `@unchecked Sendable`, `nonisolated(unsafe)`. Gaps in 1.3.0: its type-name list drops `@unchecked` (read the syntax node instead), it can't see calls inside computed properties like a SwiftUI `body` (the UI-identifier rule uses SwiftSyntax directly for view rawValue expressions, identifier declarations and the remaining dynamic-access bans in journey bodies), and it has no `switch` view (catch-all-default rule uses SwiftSyntax directly, a heuristic without type information).
- **SwiftLint `--strict`** catches force unwrap/try/cast and, with a comment-matching custom rule, **every** suppression comment, including `disable all` and a comment that disables the ban itself. Its baseline tolerates existing violations and fails new ones.
- **State-flow trial (TCA 1.26.2 vs Mobius 0.8.0):** neither stops I/O inside reducers/update functions (now rule `no-io-in-logic`). TCA's macros need `-skipMacroValidation` for command-line builds. With Tuist, every TCA runtime library must be a shared framework, except `CasePathsMacrosSupport`, which macros use and must stay static. Mobius tests built on async streams hang rather than fail when logic breaks.
- **Simulators:** device-specific runtimes (e.g. `iOS-27-2-iPhone19-4`) can fail to prepare for tests; the tests gate picks devices from the standard iOS runtime.
- **Journey module boundary (Swift 6.4.2 swiftlang-6.4.2.1.9, Xcode 27.2 27B52, iOS Simulator SDK 27.2):**
  - XCTest re-exports XCUIAutomation: raw lookups still compile in an XCTestCase target with library evolution. A public XCTestCase facade still requires XCTest in clients (`missing required module 'XCTest'`). Journey bodies therefore live in `AppVerifyJourneys` without testing search paths; generated adapters retain XCTestCase inheritance and Class/testName identities.
  - Resilient JourneyKit keeps XCTest internal and wraps both app and elements. Xcode's explicit scanner rejects SDK imports with `Compilation search paths unable to resolve module dependency: 'XCTest'`; standalone typecheck reports `no such module 'XCTest'`. A testable Core import fails the scanner's compatible-module check; standalone typecheck says Core was not compiled for testing.
  - Core is **not** resilient. A resilient Core makes its enums non-frozen, so a `switch` over one outside Core needs `@unknown default` and a new state no longer breaks unhandled sites (`exhaustive-states/pass-all-handled` fails). The cost is one warning in JourneyKit's build: "module 'Core' was not compiled with library evolution support; using it means binary compatibility for 'JourneyKit' can't be guaranteed". It exits **0 even with `-warnings-as-errors`**, belongs to no diagnostic group, so it can't be silenced on its own, and binary compatibility doesn't matter here: JourneyKit is always built with its clients (Swift 6.4.2, Xcode 27.2).
  - The unchanged literal-conformance attack fails first because its public extension uses an internal Core import. An added public-import variant still cannot reach UIID's initializer (`no exact matches in call to initializer`). Compiler cases also cover private handles, typed arguments, raw types, extensions, module selectors, deprecated callers, coordinates and AnyObject lookup. Reflection/Objective-C dispatch and unsafe memory access remain syntax bans; verify rejects handwritten adapters.
  - Fixture records, screenshot attachments and xcresult processing retain their contracts. Tuist embeds the new frameworks in the UI-test bundle; built files and the isolated test plan were inspected. Simulator verification and the full rule suite are intentionally owed to the parent run (machine capacity constraint).
- **Verification (XCUITest, Xcode 27.2):**
  - Swift Testing can't drive UI; journey adapters are `XCTestCase`s.
  - `xcodebuild test` puts the build folder first on the runner's and app's `DYLD_FRAMEWORK_PATH`. TCA's dependency swift-sharing builds `Sharing.framework`, the name of a private iOS framework, so the runner loaded it in place of Apple's and crashed before any test ran (`DEDSupport` category, "missing from an installed root"). Our `Settings` module also shares a name with a private iOS framework. `verify.py` runs from a copy of the `.xctestrun` without the build folder on those paths. The app and test bundle embed their own frameworks, so they run as the shipped app would.
  - A SwiftUI `Text` row in a `Form` is exposed as a cell, not static text; a `Toggle` is a switch inside a switch, and only the inner one toggles.

  - agent-device's runner can take the foreground after a launch; `agent-device open <bundle id>` brings the app back without relaunching it.
  - Tuist `--only redundant`, newly added to the gate, found an unused `SettingsTests → Core` dependency.
  - Harmonize 1.3.0's `productionCode()` skips files under a folder whose name ends in `Tests` or `Fixtures`, matched against the path relative to the scope's base (`testCode()` is only those). `module-boundaries` scopes each module with `.on("Targets/<module>")`, which makes the module folder the base, so `Targets/Fixtures` *is* checked (case `fail-fixtures-imports-swiftui`). Outside the package the initializer isn't even a candidate: a call reports "no exact matches in call to initializer", not an access error. Within one package it is not a wall, as the 2026-11-15 decision notes.

Seen on unchanged journeys: a tap the app never received (the switch stayed on for the whole 10 s wait, and the saving indicator never appeared), an app launch that took about 190 s and then failed with `kAXErrorServerNotFound`, and "Failed to determine hittability of Switch … Activation point invalid". 2 of 6 runs of `testTurningOffSurvivesRelaunch` failed this way. A later trial (decision above) saw no failure in 63 steady-load runs, and reproduced dropped taps and "never became hittable" when three fresh simulators booted and ran journeys together. Each dropped tap was the save-fails journey's tap, the first after the app's first launch on that device, and that launch took 20–35 s (about 135 s in the first reproduction).
  - Concurrent XCUITest runs on one Mac can fail together: in the trial's warm-up, three xcodebuild processes on three brand-new simulators launched, tapped and failed together, finishing within 0.3 s of each other (Xcode 27.2, iOS 27.2); later rounds weren't synchronized and had mixed outcomes. Count concurrent runs as correlated, not independent, when measuring flakiness.
- **Harmonize 1.3.0 tests hang when run in parallel** (seen with 10 rules: every test passes alone in about 1 s, and the full parallel run never finished in 2 hours). The gate runs them with `--no-parallel`; the full set takes about 1 s.

Each Xcode build already uses every core, and booted simulators' disk images and the build folders share one external drive: with 2 rule-suite workers each worker's busy time rose about 1.6 times, and with 3 simulators the load average passed 300 and journeys failed with `kAXErrorServerNotFound` and runner timeouts. A freshly cloned simulator runs its first-boot services for minutes. Re-measure on a faster machine before turning parallelism on by default.
- **Tuist 4.216.7 caches a manifest's output** by the manifest and helper sources: a `Project.swift` that reads a data file keeps the old project when only that file changes (`tuist dump project` probe), while an edit to a `Tuist/ProjectDescriptionHelpers` file is picked up. That's why the feature declaration is a Swift helper. SwiftPM (Swift 6.4.2) refuses a target path outside the package root ("is outside the package root") but builds symlinked source files and rebuilds when the linked file changes, so `Rules/` compiles the same shape through links.
- **Tool details that bite:** Python's `zipfile` breaks macOS framework symlinks (use `ditto`); a placeholder type named like its module (`enum Core` in `Core`) breaks module-qualified lookup.

- **Process death:** `am kill` ends only a process in the background, as the system does for memory, and keeps the task and its saved state (`am force-stop` discards them). Starting the same component again (`am start -n`) brings that task back: the Activity is recreated with its saved state and its first intent, the ViewModel is new, and `SavedStateHandle` keeps its values.
- **Android:** apps targeting API 37 draw edge to edge: with the default theme's action bar, the tally's field and button sat under it and every tap hit the bar (found by the first journey run; fixed with a no-action-bar theme and `safeDrawingPadding`). avdmanager records the system image relative to its own folder's parent, not the SDK, so the emulator couldn't find it until emulator.py rewrites `image.sysdir.1`. Compose test tags reach UiAutomator as resource ids only under `testTagsAsResourceId`, which `Modifier.uiId` sets. A self-instrumenting `com.android.test` module runs journeys in their own process, so they can stop and relaunch the app. The emulator cold-boots headless in about 25 s from the external drive; the five tally journeys take about 35 s.
